    ASH configuration and defaults¶

    ASH has independent settings for stored codes, construction, query projection, and query execution. This reference covers library parameters and BenchYAML controls. The BenchYAML Guide defines the index YAML fields. Recipes specify their own graph and compression values.

    Set JVM properties before the affected model, provider or executor is initialized. Query views and pools are cached; changing a property later does not reconfigure existing objects. CPU-count properties do not pin threads.

    Similarity¶

    An ASH model is trained for one similarity, DOT_PRODUCT, EUCLIDEAN or COSINE, which AsymmetricHashing.initialize requires as its second argument, as GraphIndexBuilder does; an ASH index cannot be built without one. The model saves it, and its codes and every scorer of them use it; asking a scorer for another similarity throws IllegalArgumentException, and every ASH score function reports it in similarityFunction(), which adaptive stopping reads. You name the similarity only where a model or index is created (AsymmetricHashing.initialize, StreamingASHIndex.coldStart); the ASH build score provider, block scorers, query preparers and StreamingASHIndex.withModel take it from the model, and an ASH index's reranker rejects any other similarity. PQ and BQ keep choosing the similarity per call. CompressedVectors.similarityFunction() returns the fixed similarity, or null when each call chooses it. BenchYAML takes the similarity from the dataset's metadata (similarity_function in dataset-metadata.yml).

    ASH does not require normalized vectors for any similarity. Training and encoding center each vector on its landmark and use the unit residual (x - mu) / ||x - mu||, so vector lengths are kept. Scores use the exact scale of VectorSimilarityFunction: (1 + dot) / 2 for DOT_PRODUCT and 1 / (1 + d^2) for EUCLIDEAN and (1 + cos) / 2 for COSINE.

    EUCLIDEAN uses the same codes, kernels and speed as DOT_PRODUCT (ASH paper, Appendix A). Its header stores -||x - mu||^2 / 2 where a DOT_PRODUCT header stores <x, mu> - ||mu||^2, and its query term is -||q - mu||^2 / 2 in place of <q, mu>, so the kernels estimate -||q - x||^2 / 2. A EUCLIDEAN model also stores a power-of-two unit that scales vectors to about unit length, so the half-precision header holds squared distances of vectors of any length.

    COSINE normalizes vectors as VectorUtil.l2normalize does when it trains and encodes, and normalizes each query in FP32 before projection and before any FP16 or INT8 conversion; it then uses the DOT_PRODUCT path, so it has the same speed and, for vectors already of unit length, the same codes and scores. Reranking with stored full-precision vectors gives exact cosine similarity. Cosine is undefined for a zero vector: a COSINE model or index throws IllegalArgumentException for a zero vector when it trains, encodes, inserts or searches, as l2normalize does, so callers must reject zero vectors first.

    Indexing:

    // The similarity is fixed here and saved with the model.
AsymmetricHashing ash = AsymmetricHashing.initialize(vectors, VectorSimilarityFunction.EUCLIDEAN,
        AsymmetricHashing.ITQ, encodedBits, 1, bitsPerDimension, executor);
ASHVectors codes = ash.encodeAll(vectors, executor);
// Graph construction scores by the model's similarity; another one is rejected.
var builder = new GraphIndexBuilder(BuildScoreProvider.ashBuildScoreProvider(codes),
        vectors.dimension(), 32, 100, 1.2f, 1.2f, true);
var graph = builder.build(vectors);

    Scoring:

    VectorSimilarityFunction similarity = codes.similarityFunction(); // EUCLIDEAN
var approximate = codes.scoreFunctionFor(query, similarity);
var reranker = vectors.rerankerFor(query, similarity);
try (var searcher = new GraphSearcher(graph)) {
    var result = searcher.search(new DefaultSearchScoreProvider(approximate, reranker), 10, 50, 0f, 0f, Bits.ALL);
}

    A fused index reads the similarity from its saved model: view.approximateScoreFunctionFor(query, similarity) must be given the same one. StreamingASHIndex takes the similarity when it is created and trains every model for it.

    Stored codes and training¶

    BenchYAML puts these under compression[].parameters with type: ASH. Construction compression controls graph scoring. Search compression selects the codes stored with a fused ASH graph.

    Parameter Default / requirement Optional values and definition
    optimizer Required ITQ (1): iterative-quantization transform. RANDOM (2): random transform.
    encodedBits Exactly one of this and compressionRatio Total stored bits including the 40-bit / five-byte header. The positive payload encodedBits - 40 must be divisible by bitsPerDimension.
    compressionRatio Alternative to encodedBits BenchYAML accepts 8, 16, 32, 64, 128, 256. Resolves a payload near the requested FP32-to-code ratio, with a minimum 64-bit payload and whole projected dimensions; inspect the printed resolved size.
    bitsPerDimension (b) 1 Integer 1 through 9, all supported by fused ASH. 1, 2 and 4 have the most optimized kernels (see below). Stored-code precision is independent of query-projection arithmetic.
    landmarkCount (C) 1 Integer 1 through 256 for the quantizer. Symmetric graph-construction scoring currently requires C=1.
    Projected dimension (d) Derived, not a separate YAML field d = (encodedBits - 40) / b, with 1 <= d <= D for input dimension D. Increasing d or b increases code size.

    For an exact payload, use encodedBits = 40 + d*b. For example, a 256-D input projected to 128 dimensions at four bits uses encodedBits: 552. Include the header when comparing memory budgets with other quantizers.

    Choosing the projected dimension for speed¶

    For the fastest construction and search, use b = 1, 2 or 4 and make d a multiple of 64. The native kernels then process whole 64-bit words and whole SIMD vectors, with no leftover dimensions:

    • Construction compares stored codes with each other. At 1 bit, the kernel works in words of 64 dimensions. At 2 bits, it works in words of 32 dimensions. At 4 bits, it works in vectors of up to 128 dimensions.
    • Search builds per-query lookup tables in 16-byte chunks of code and projects queries 32 output dimensions at a time.

    Other values of d are correct and handled in one extra masked step, so the penalty is small. In the measurements below, a 2-bit code at d = 380 costs about 20-30% more per construction comparison than at d = 384, and search QPS differs by about 1.5%. When a byte budget lands just short of an aligned d, prefer the aligned value. For example, with a 384-D input and a 100-byte budget, d = 384 at 2 bits (101 bytes, no dimension reduction) is a better choice than d = 380 (100 bytes).

    The other widths, b = 3 and 5 through 9, store each dimension as an unsigned b-bit field. Search scores their graph neighborhoods with the projected query rounded to INT8 and integer dot products (VNNI on x86 processors that have it), so make d a multiple of 8. Their other asymmetric scoring uses the same 4-bit query tables as 2 and 4 bits. Construction still compares their codes with a portable per-dimension path, so building is slower than at 1, 2 or 4 bits; native code-to-code kernels for these widths are left for future work.

    Construction comparison cost, in ns per code pair, on one pinned core with the native provider, on an Intel Xeon 6985P-C and on an AWS m6id.4xlarge (Ice Lake).

    b d Xeon 6985P-C m6id.4xlarge
    2 192 9.3 16.7
    2 380 16.6 30.0
    2 384 13.8 22.5
    4 190 15.2 24.0
    4 192 14.5 24.1
    4 384 18.4 28.5

    Training and base encoding retain their FP32 projection path; some training statistics and factorizations use FP64 internally. Query precision does not change the trained model, base encoding, stored-code layout or index format.

    Graph construction¶

    BenchYAML selects construction scoring through compression[].scoring on an ASH construction entry. Omission uses the JVM policy, which defaults to symmetric-all. For example, this JVM property selects mixed scoring:

    -Djvector.bench.ashConstruction=symmetric
    Property value Insertion search Existing-node / diversity scoring
    symmetric-all (default) Encoded vector against encoded vectors; no dense insertion-query projection Symmetric encoded scoring
    symmetric Original vector used as an asymmetric query Symmetric encoded scoring
    symmetric-scalar Original vector used as an asymmetric query Scalar symmetric scoring; diagnostic control
    asymmetric Original vector used as an asymmetric query Original vector used as an asymmetric query; diagnostic control
    asymmetric-cached Original vector used as an asymmetric query Cached asymmetric query state per node; diagnostic control with extra memory use

    jvector.bench.ashConstruction controls BenchYAML/Grid, not every library builder. For library integration, obtain a provider using BuildScoreProvider.ashBuildScoreProvider(encoded). Use builder.addGraphNode(node, provider.searchProviderFor(node)) for fully symmetric insertion. The overload taking an original vector retains asymmetric query preparation. Both policies use the same stored ASH vectors; application queries continue to use asymmetric scoring.

    Construction policy can change the graph, recall and QPS. Use fresh indexes when comparing modes: the graph cache key does not include this JVM property, so changing it does not invalidate an existing cached graph.

    Encoding while vectors arrive¶

    To build a graph while its vectors stream in with a fixed model, ash.vectorsBuilder(capacity) encodes batches from any number of threads into distinct ordinals. Its live() view scores codes while they fill in, so a graph can be built over them at the same time; score a code only after its batch is encoded. build(size) returns the finished, immutable ASHVectors. Ordinals never encoded keep the all-zero code. For an index whose model changes while it grows, StreamingASHIndex uses MutableASHVectors, which re-encodes its pages for a new model one at a time.

    In-memory code layout¶

    ASHVectors keeps one copy of the codes, in compact pages. Each vector's code body sits back to back with the others: sign words at 1 bit, sign-magnitude projection codes at 2 and 4 bits, and offset-binary fields at the other widths (dimension j is the unsigned field at bits [j*b, (j+1)*b), with value field - (2^b - 1)/2). Every stored offset includes the landmark term -scale * <A mu_c, code>, so asymmetric scoring needs only Aq. Bodies have no per-vector object, array or padding. Scale, offset and landmark are decoded once into three parallel arrays. Every scorer, symmetric and asymmetric, reads the codes in place, and the encoder writes straight into the pages.

    Retained memory per vector is the serialized size plus 4 bytes, because the two binary16 header fields are held as floats: for example 101 bytes on disk and 105 bytes in memory for 768-D at 32x. Pages hold up to 256 KiB, which keeps them below G1's smallest humongous-object threshold so the collector never rounds them up to whole regions. ASHVectors.get(i) returns an allocated copy; copyTo(i, dest) fills reusable storage. Optional caches built for block scoring (blockScorerFor with a block size) hold a second, interleaved copy and are charged in ramBytesUsed() when created; graph construction and search do not build them.

    Query projection and scoring¶

    JVM property Default Optional values and definition
    jvector.ash.queryProjection auto auto: INT8 where an integer dot-product backend exists, then optimized FP16, falling back to FP32. fp32: FP32. fp16: require optimized FP16 with FP32 accumulation/output. int8: require INT8 projection with integer accumulation and FP32 output. Explicit unsupported precisions fail. Default for models without query options set in code.
    jvector.ash.singleKernel auto auto, scalar, simd; single-vector ASH scoring kernels, subject to provider/format support.
    jvector.ash.blockKernel auto auto, scalar, simd; blocked/fused ASH scoring kernels, subject to provider/format support.
    jvector.ash.queryBatchSize 8 Positive integer below Integer.MAX_VALUE; maximum opportunistic batch for model-owned synchronous query preparation; 1 disables combining. Separate from the queued batch limit below. Default for models without query options set in code.
    jvector.ash.gatheredScoring false Experimental. true scores a node's neighbors from in-memory 2- or 4-bit codes as one gathered block, as fused ASH scores its stored neighborhoods (one landmark, backend support required). It lowers single-query latency, but with every core busy it has measured 1–6% lower throughput.

    Single-vector scoring (separated codes, streaming indexes and fused upper layers) depends on the bit width. 1-bit codes use a SIMD masked add over their sign bits. 2- and 4-bit codes use a projection dot that decodes codes in registers: native Highway kernels, or with Panama a contiguous-query kernel on JDK 25+ and a query-gather kernel on earlier JDKs. The other widths use the native nibble-LUT dot; with Panama they are decoded in scalar Java, so prefer 1, 2 or 4 bits there. Fused graphs score base-layer neighborhoods with whole-block kernels at every width.

    To choose these per model in code, call setQueryOptions before the model projects its first query, for example right after opening an index. Later calls throw IllegalStateException, because the prepared projection is fixed for the model's lifetime.

    var ash = ((FusedASH) index.getFeatures().get(FeatureId.FUSED_ASH)).getASH();
ash.setQueryOptions(ASHQueryProjection.AUTO, 1);  // precision, maximum batch

    See Choosing ASH query-projection precision for processor guidance and FP16/INT8 requirements. Under symmetric-all, query precision affects application queries, not insertion search. Under mixed or asymmetric construction, it can affect insertion too.

    BenchYAML precision selection¶

    Set queryProjection in the parameters map of an ASH compression entry. See ASH query parameters for values and JVM precedence. ASH CSV rows record ash_query_projection_requested and ash_query_projection_effective; the latter is read from the prepared view, with fp16+fp32 indicating observed automatic FP32 range fallback. Non-ASH rows have blank precision columns; an unused projection has blank effective precision. See the precision guide.

    Providers, CPU budgets and serialization¶

    Setting Default Optional values and definition
    jvector.vectorization_provider Automatic selection native, panama, default (scalar). Supported Java 22+ runtimes prefer native, with existing fallbacks. Explicit native requires successful loading.
    jvector.enable_native_vectorization true true / false; automatic native selection. Explicit provider selection overrides it. Deprecated jvector.experimental.enable_native_vectorization is a lower-precedence alias.
    jvector.physical_core_count OS topology detection bounded by available processors; fallback heuristic Positive thread budget for JVector's bounded pool and queued workers. Construction and queries can use separate budgets/processes; see Thread budgets.
    -XX:ActiveProcessorCount JVM/container detection Positive processor count exposed to the JVM; coordinate with allocated physical cores. Does not set affinity.
    --add-modules=jdk.incubator.vector Not added by the application Enables the Vector API module needed by SIMD providers on supported runtimes.
    --enable-native-access=ALL-UNNAMED JVM native-access policy Native access for classpath deployments. Named-module deployments should enable the relevant module.
    -Xms, -Xmx JVM ergonomics Initial / maximum heap; account for resident input, model and construction memory.
    -ea, -da Assertions normally disabled Enable / disable Java assertions; independent of numerical precision.

    Thread budgets¶

    Graph insertion mostly waits on memory, so a second hardware thread per core fills those stalls: give construction every hardware thread, for example -Djvector.physical_core_count=16 -XX:ActiveProcessorCount=16 on 8 cores with two threads each, or pass a pool of that size to the builder. Builds of millions of vectors gain the most; recall and the built graph's search speed do not change. Compute-bound search runs best with one worker per physical core. Search that waits on storage needs more queries in flight than cores; see Building and serving larger-than-memory indexes.

    BLAS threads¶

    ASH training is the only BLAS and LAPACK user. JVector sets the native BLAS thread count for its own calls, so a host does not need to configure MKL or OpenBLAS: training uses one BLAS thread, or as many as the executor passed to AsymmetricHashing.initialize(..., ForkJoinPool executor). Queries never call BLAS. With the native provider, MKL applies the count per calling thread (MKL_Set_Num_Threads_Local). OpenBLAS has only a process-wide count (openblas_set_num_threads; its openblas_set_num_threads_local also sets the process-wide count), so JVector sets it for the duration of training, and trainings running at the same time on other threads share the first one's count until the last finishes. Other providers leave BLAS threading to MKL_NUM_THREADS, OMP_NUM_THREADS and OPENBLAS_NUM_THREADS. io.github.jbellis.jvector.util.BlasThreads applies the same limit to a host's own BLAS work.

    BenchYAML trains in its construction pool, so BLAS uses construction.workers threads (all physical cores by default). Set MKL_DYNAMIC=FALSE so MKL uses the count it is given. The ASH versus PQ study scripts also set the thread variables, to one for queries and the core budget for construction, as in the published runs. OS affinity (numactl --physcpubind) and memory placement (--membind, --interleave) are deployment choices.

    Query delivery and measurement controls¶

    Set BenchYAML query delivery in the search section (queryExecution, requestsPerWorker) and the ASH batch limit in the ASH search parameters. Database integrations select their own admission policy and executors. See Integrating ASH queries into a database.

    Setting Default Optional values / definition
    jvector.bench.queryThreads 0 Direct caller count: 0 uses common pool, 1 is serial, larger positive values use a dedicated caller pool. Does not set queued worker count.
    jvector.bench.verifyConcurrentResults false true / false; validate concurrent results against reference results.
    jvector.bench.runConfig jvector-examples/yaml-configs/run-config.yml Run YAML path for measured benchmarks, console and CSV fields.
    jvector.bench.sourceRef Unset Source identity for provenance; no numerical effect.

    Run YAML benchmarks, console and logging select computed/reported throughput, recall, latency and visit counts, and measurement sets warmup, timed passes and the page cache state; see Run configuration. Construction separately reports quantizer training, encoding, NVQ training and graph/write. The throughput benchmark can also report per-query response times, page reads per query and, for queued execution, mean batch size. Unloaded latency and loaded response time describe different measurements. Independent build/query JVM repetitions are launch choices, not model defaults; preserve individual CSVs.

    The ASH versus PQ case script (run-ash-pq-benchmark.sh) accepts JVECTOR_BENCH_DATA_DIR (required: where datasets are downloaded and reused), JVECTOR_BENCH_BUILD_SMT, JVECTOR_BENCH_ADAPTIVE, JVECTOR_BENCH_OVERQUERY, JVECTOR_BENCH_HEAP (128g) and JVECTOR_BENCH_NUMA_POLICY (bind:0; alternatively interleave:<nodes>). These defaults belong to the script, not the library. See Reproducing ASH versus PQ for launch and artifact details.
