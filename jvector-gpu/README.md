# jvector-gpu: graph construction on NVIDIA GPUs

`jvector-gpu` builds JVector graph indexes on an NVIDIA GPU, using [TornadoVM](https://github.com/beehive-lab/TornadoVM)
and NVIDIA [cuVS](https://github.com/rapidsai/cuvs). The result is an ordinary JVector graph, with hierarchy, and
search, writers and on-disk formats are unchanged.

Graph build time on an RTX 4090 against JVector on a 13th-gen i9 (i9-13900K, 32 threads), at the same settings
(M=32, efConstruction=100, overflow 1.2, alpha 1.2, hierarchy). Recall@10 for both is from the same search (topK 10,
rerankK 50). Measured in October 2026 on JVector 4.0.1 with TornadoVM 7.x; the re-measurement on JVector 4.1.0 with
TornadoVM 8.0.0 follows the table.

| dataset | similarity | vectors | JVector (CPU) | jvector-gpu | speed-up | recall@10 CPU / GPU |
|---|---|---|---|---|---|---|
| Cohere Wikipedia v3, 10M\* | COSINE | 10,000,000 x 1024 | 2270.7 s | 207.1 s | 11x | 0.8752 / 0.8970 |
| ada002-1M | COSINE | 982,790 x 1536 | 268.4 s | 14.1 s | 19x | 0.9692 / 0.9727 |
| glove-100-angular | COSINE | 1,183,514 x 100 | 52.5 s | 8.0 s | 6.5x | 0.7430 / 0.7755 |
| sift-128-euclidean | EUCLIDEAN | 985,462 x 128 | 36.3 s | 7.9 s | 4.6x | 0.9564 / 0.9645 |
| lastfm-64-dot | DOT_PRODUCT | 292,385 x 65 | 4.3 s | 2.6 s | 1.6x | 0.9575 / 0.9597 |

\* The first 10M English rows of `CohereLabs/wikipedia-2023-11-embed-multilingual-v3`, with 10k held-out queries
and exact ground truth. The GPU build reads the vectors in place with `MappedVectors`. cuVS builds the candidates
in 9 overlapping batches (143 s), and the FP16 vectors take 20.5 GB on the device. At every search beam the GPU
graph has the higher recall@100 (e.g. 0.926 vs 0.912 at beam 200).

Re-measured on JVector 4.1.0 and TornadoVM 8.0.0 (`run.sh wikipedia <dir> gpu|cpu`): Cohere Wikipedia v3,
1,000,000 x 1024, COSINE. The GPU build takes **17.4 s** (median of 4 cold runs, 16.0-19.0 s) against **181.7 s** for
JVector on the CPU, about 10x. Recall@10 by search beam:

| beam | 20 | 40 | 80 | 160 |
|---|---|---|---|---|
| JVector (CPU) | 0.8117 | 0.8934 | 0.9459 | 0.9741 |
| jvector-gpu (3 runs) | 0.8060-0.8073 | 0.8943-0.8960 | 0.9476-0.9485 | 0.9761-0.9766 |

GPU times are for a single cold build in a fresh JVM, JIT compilation of the kernels included (a warm 1M x 1536
build takes about 10-12 s). The speed-up grows with the dimension and the dataset size.

## How it works

`TornadoGraphBuildAccelerator` implements JVector's `GraphBuildAccelerator` SPI:

1. **Candidates.** cuVS NN-Descent computes the approximate 96-NN graph of all vectors, through TornadoVM's cuVS
   provider. Datasets larger than device memory are built in overlapping batches from host memory. Meanwhile the
   CPU prepares step 2: it packs the vectors to FP16 and compiles the GPU kernels. This happens only when the
   dataset fits on the device; otherwise cuVS needs the host memory.
2. **Diversity pruning, on the GPU.** This is JVector's rule, with the builder's alpha. Each node's list is pruned
   from its first 48 candidates when that is enough, and from all 96 otherwise. "Enough" is tested on a sample of
   4096 nodes: if pruning their short lists still fills at least 95% of them to the max degree, more candidates
   would only be dropped. For typical embeddings this halves the pruning work. For data where the short lists
   come out short, such as clustered EUCLIDEAN data, the build keeps 96. The Gram matrix of each
   node's candidates is computed with tensor cores (`mma.sync`, FP16 inputs, FP32 accumulation; the kernel is
   generated by `codegen/gen_gram_mma_packed.py`). One work-group per node then applies the rule, with scores in
   JVector's units for COSINE, DOT_PRODUCT and EUCLIDEAN.
3. **Reverse edges** are merged on the CPU, and the lists that grew are pruned again on the GPU.
4. **Upper layers** use JVector's level distribution (`GraphIndexBuilder.sampleGraphLevels`). The levels are
   drawn before the build starts, so the vectors of the upper-layer nodes are copied out during step 1. Each layer
   is built like the base layer, from exact candidates, on the GPU while the CPU installs the base layer.
5. The lists are installed with `GraphIndexBuilder.addGraphNodeWithNeighbors`. `cleanup()` and everything after it
   are JVector's own.

Supported: COSINE, DOT_PRODUCT and EUCLIDEAN; any dimension (rows are padded to a multiple of 16); max degree up
to 64; up to `4 x 2^31` FP16 values (e.g. 10M x 1024). Datasets in a raw float32 file can be read in place with
`MappedVectors`. In every other case `supports()` returns false and JVector builds on the CPU as usual.

Not supported: incremental insertion and deletes, which stay on the CPU path, and non-NVIDIA GPUs.

## Also on the GPU: compaction and product quantization

**Compaction by rebuilding.** `GpuCompaction` takes the same inputs as `OnDiskGraphIndexCompactor`: on-disk sources
with inline vectors and their live nodes. It reads the live vectors back and builds the merged graph from scratch on the
GPU. As with `OnDiskGraphIndexCompactor`, the compaction assigns the new ordinals and `ordinalMappers()` returns them
afterwards (on the GPU the live nodes are numbered in source order). When the GPU build isn't available, it falls back
to `OnDiskGraphIndexCompactor`.

```java
var compaction = new GpuCompaction(sources, liveNodes, VectorSimilarityFunction.COSINE);
compaction.compact(outputPath);
List<OrdinalMapper> newOrdinals = compaction.ordinalMappers();   // as OnDiskGraphIndexCompactor.ordinalMappers()
```

ada002-1M, 4 segments built by JVector on the CPU (M=32, hierarchy):

| | time | p50 search latency at equal recall@10 |
|---|---|---|
| `OnDiskGraphIndexCompactor` | 291.6 s | baseline |
| `GpuCompaction` (read 0.4 s, build 14.4 s, write 4.4 s) | **19.2 s (15.2x)** | 5-17% lower (0.86-0.99 recall) |

The rebuilt graph is a fresh build rather than a stitched one, so at the same beam it has slightly higher recall.

**Product quantization.** `GpuProductQuantization.compute` trains PQ codebooks the way `ProductQuantization.compute`
does (unweighted): the same subspaces, training sample, k-means++ seeding and Lloyd iterations. `encodeAll`
encodes with any unweighted `ProductQuantization`, including one trained on the CPU. Both return JVector's own
`ProductQuantization` and `PQVectors`. Both use JVector's CPU code when TornadoVM isn't present, or when a subspace
is wider than 32 dimensions.

ada002-1M, M=192, K=256:

| | train | encode | total | recall@10 of a PQ scan |
|---|---|---|---|---|
| JVector (CPU) | 10.01 s | 3.55 s | 13.56 s | 0.8037 |
| GPU | 2.85 s | 0.95 s | **3.80 s (3.6x)** | 0.8071 |

Encoding with JVector's own codebooks on the GPU gives JVector's codes except exact ties: 23 of 188,695,680 codes, where two centroids are equally close up to float rounding (relative difference ≤ 1.5e-7) and the GPU picks the other one.

`jvector-gpu/run.sh check` covers both:
* compaction: 4 segments with 10% of the nodes deleted;
* PQ: JVector's codes, and recall within tolerance.

## Requirements

* An NVIDIA GPU with tensor cores, Ampere (sm_80) or newer, and its driver.
* JDK 22 or newer, and the [TornadoVM](https://github.com/beehive-lab/TornadoVM) SDK 8.0.0 with the CUDA
  backend (`tornadovm-8.0.0-jdk22plus-cuda`, the released SDK), with its `bin/` on the
  `PATH`. The build takes `tornado-api` and `tornado-cuvs` 8.0.0 from Maven Central.
* NVIDIA cuVS 26.08. `jvector-gpu/cuvs-env.sh` downloads it (2.1 GB of wheels, including the CUDA libraries it needs)
  into `~/.jvector-gpu/cuvs` the first time and puts it on `LD_LIBRARY_PATH`; any `python3` with `pip` will do.

## Build

The module is only built with the `gpu` profile. As for any JVector build, the clone needs its submodules
(`jvector-native` uses Google Highway):

```bash
git clone --recurse-submodules https://github.com/datastax/jvector.git && cd jvector
mvn -Pgpu -pl jvector-gpu,jvector-examples -am package -DskipTests
```

## Run

`jvector-gpu/run.sh` sets up cuVS and runs under TornadoVM's `tornado` launcher, with the device memory budget
sized to the GPU:

```bash
jvector-gpu/run.sh check                     # GPU vs JVector: build (every similarity), PQ and compaction; prints OK
jvector-gpu/run.sh bench ada002-100k         # JVector's Bench, graphs built on the GPU
jvector-gpu/run.sh cpu ada002-100k           # the same Bench on the CPU, for comparison
jvector-gpu/run.sh check base.fvecs query.fvecs gt.ivecs COSINE   # any dataset
```

Outside the script, the accelerator is selected with `-Djvector.graph.accelerator=tornadovm` on a JVM started by
`tornado`, with `jvector-gpu.jar` on the class path and cuVS on `LD_LIBRARY_PATH`. `-Dtornado.device.memory` must
cover the vectors in FP16 (`n x dim x 2` bytes) plus about 0.5 GB; TornadoVM's default, 4 GB, is enough for
1M x 1536. If it is too small, the accelerator declines and logs the setting to use.

Options (system properties):

| property | default | meaning |
|---|---|---|
| `jvector.gpu.candidates` | auto | candidates per node to prune from; by default 48 or 96, chosen from the data (see How it works) |
| `jvector.gpu.nndIterations` | 8 | NN-Descent iterations |
| `jvector.gpu.clusters` | auto | cuVS batches for the candidate graph (more than 1 when the dataset exceeds device memory) |
| `jvector.gpu.overlap` | 2 | batches each vector joins when the candidate graph is built in batches |
| `jvector.gpu.trace` | false | print the time of each phase |

## More on the GPU (2026-10-09)

Measured on an RTX 4090 against an i9-13900K (32 threads).

- **NVQ encoding** (`GpuNvq.encodeAll`): JVector's 8-bit NVQ with the same growth-rate search, one work-group
  per (vector, sub-vector). It returns JVector's own `NVQVectors`. On ada002-1M it takes **1.34 s against 4.06 s
  (3.0×)**, with identical recall@10 of an NVQ-scored scan (0.9974). 99.995% of the code bytes and 96.9% of the
  growth rates are identical; the rest are near-ties, because the GPU sums each loss in a different order.
  `run.sh nvq <dataset>`.
- **Exact ground truth** (`run.sh groundtruth`): cuVS brute force over base chunks. Wikipedia 10M × 1024 takes
  **24.5 s against numpy's 681 s**, with 99.997% top-10 agreement with the CPU (ties among duplicate passages).
- **Where an on-disk build's time goes** (`run.sh phases <dataset>`, ada002-1M): GPU build 11.2 s, NVQ encode
  4.3 s a pass (JVector's `Bench` encodes twice), inline writes 2.8–7.0 s a format (`writeInline` is
  synchronized), fused-PQ final write 5.6 s.
- **Fused PQ is not a GPU job.** Its write copies each neighbour's PQ code into a new array (`compressed.copy()`)
  and writes it: about 31M small allocations at 1M, and no computation. The fix is on the CPU, in JVector core,
  by writing slices without the copy.
