### PQ Training No Longer Copies the Training Set to Center It

**Description**

`ProductQuantization.compute` and `refine` with `globallyCenter = true` subtracted the global centroid from
every training vector, building a second full-size copy of the training set that stayed alive for the whole
k-means run. They now subtract the matching centroid slice from each subvector as it is extracted for a
subspace, in the same pass that copies the slice (`VectorUtil.sub(vector, offset, centroid, offset, size)`).
The values k-means sees are identical, the caller's vectors are never modified, and no centered copy
is allocated. See [#807](https://github.com/jbellis/jvector/issues/807).

**How to Enable**

No configuration is required.

**Notes**

Training PQ with 256 subspaces and 256 clusters on 128,000 x 1024-dimension vectors needed between 1000 and
1200 MB of heap on the previous code and completed at 700 MB (the lowest tried) with this change, against a
524 MB training set. Encoding still allocates a short-lived centered vector for each encoded vector.

Centering per subspace costs one provider call per training vector per subspace (32.7M calls at that shape)
instead of one call per training vector, so the step that produces the k-means input is slower on the native
provider, where the call overhead dominates. On an AVX-512 Xeon with 4 physical cores and JDK 25, that step
(128,000 x 1024-dimension vectors, 256 subspaces, best of 5 runs) took 1.07 s on the previous code, 2.06 s
with this change on the native provider, 1.00 s versus 0.84 s on the default provider, and 0.93 s versus
0.94 s on the Panama provider. The step is a small part of the training, so the end-to-end training time is
unchanged: training 128,000 x 1024-dimension vectors with 256 subspaces and 256 clusters on the Panama
provider took 26.4 s on the previous code and 26.2 s with this change, with the peak heap down from 2.0 GB to
0.95 GB and the bytes allocated down from 2.5 GB to 2.0 GB.
