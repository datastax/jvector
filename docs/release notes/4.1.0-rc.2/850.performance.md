### Faster PQ Graph Builds at Every Subspace Width

**Description**

The native and Panama providers score PQ code pairs the same way: from a copy of the codebooks padded with zeros, so
odd and mixed subspace widths run as fast as even ones, in one native call or one allocation-free Java loop per pair.
Subspaces of 16 floats or more use a centroid-pair table, which is faster there; it is kept with the PQ vectors
being built, counted in their `ramBytesUsed()`, and freed with them. Saved and in-progress codes both gain.
PQ query tables are now built in one call per query from a transposed copy of the codebooks, with the query centered
inside the kernel, on both providers.

**How to Enable**

No configuration is required.

**Notes**

On cohere-english-v3-1M (128 subspaces of 8 floats), native on-disk builds on GNR (48 cores) took 25-31 s against
40-52 s without this change. Fixes [#845](https://github.com/datastax/jvector/issues/845).

### Panama Kernels No Longer Fall into a Slow Mode

**Description**

With the Panama provider, some JVMs left Vector API operations as calls that put every vector on the heap, so the same
build or search ran up to about 2x slower in one JVM than in the next. The PQ query table, PQ code-pair scoring, NVQ
scores, exact dot products and squared distances, and INT8 dot products now keep their vectors in registers: each kernel
does its whole job in one method compiled on its own, names its vector species directly, calls `lanewise` at its own
call sites, and states a vector's exact class where a store needs it, so a process that mixes vector sizes is far less
likely to change how the kernels compile. Results are unchanged.

**How to Enable**

No configuration is required.

### Faster ASH with the Panama Provider

**Description**

The Panama provider now scores ASH the way the native provider does: whole fused neighborhoods in one call (nibble
codes and INT8 field blocks), all rows of a symmetric comparison in one call, query projection for a whole batch of
queued queries in one call, and INT8 and FP16 query projection on request. On mpnet 1M with 2-bit codes, Panama
queries ran 49-102% faster and builds 9% faster on GNR (48 cores). The native provider remains faster and is
recommended for ASH.

**How to Enable**

No configuration is required. `jvector.ash.queryProjection=int8` or `fp16` selects those projections on Panama; `auto`
keeps FP32 there.
