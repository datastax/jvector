### Compaction: level-0 candidates found by scanning cells instead of searching

**Description**

Compaction merges several pre-built partition indexes into one. At level 0 it must give every node
its nearest neighbours in each of the *other* partitions, and until now it found them with one
graph search per node per other partition — a walk whose every hop reads a different record from a
different place on disk. Cost scales with nodes times hops, and the reads are scattered, so once the
inputs stop fitting in page cache the merge becomes bound by major faults rather than by
computation.

This change computes the same thing by scanning. Three pieces make it work:

1. **Cells.** The compactor's own upper-layer merge now runs first, and its merged level-1 nodes
   become *cells*. Every live node is assigned to the cell its vector descends to.
2. **Ordinals in cell order.** Output ordinals are assigned cell by cell, so one partition's members
   of one cell occupy consecutive rows of the output, and reading a cell is one sequential read.
3. **A shared scan.** Each node names the cells it wants, ranked by a width-64 beam over the merged
   top layer and cut off after a fixed budget of 4,096 vectors per larger partition. Those requests
   are then inverted, so a cell is read **once** per group and scored against **every** node that
   asked for it, rather than once per node.

Partitions are processed smallest first: a node scans only the partitions larger than its own, and
the reverse direction arrives as a bounded set of offers, so the largest partition scans nothing.

The merge remains exact. Every score that orders a candidate is computed on the vectors themselves.
Approximation appears in exactly two places: which cells a node asks for, and the pairwise
comparisons inside diversity selection, which run on vectors decoded from a wide PQ code. The wide
code measures slightly *better* there than exact comparisons, because coarse codes collide
near-duplicates and near-duplicate detection is what the diversity test exists to do.

**Breaking API change**

`OnDiskGraphIndexCompactor` now assigns its own output ordinals, because locality in the output
ordinal space is what makes a cell's members contiguous and therefore readable in one pass. A
caller-supplied mapping cannot provide that. Both constructors lose their `remappers` parameter and
the mapping is published afterwards:

```java
// before
new OnDiskGraphIndexCompactor(sources, liveNodes, remappers, similarityFunction, executor);
new OnDiskGraphIndexCompactor(sources, sourceCompressed, liveNodes, remappers, similarityFunction, executor);

// after
new OnDiskGraphIndexCompactor(sources, liveNodes, similarityFunction, executor);
new OnDiskGraphIndexCompactor(sources, sourceCompressed, liveNodes, similarityFunction, executor);

// then, once compact() has run:
List<OrdinalMapper> mappers = compactor.ordinalMappers();
```

Callers that previously passed `OrdinalMapper.OffsetMapper` simply drop the argument and read
`ordinalMappers()` afterwards to learn where each source node landed. `oldToNew` of a deleted node
is `OrdinalMapper.OMITTED`; live ordinals are dense.

Also removed: `setRefineAfterCompaction` and the optional refinement pass it gated.

Both `compact(Path)` and `compact(Path, Path)` are unchanged, as is the requirement that every
source carries the `INLINE_VECTORS` feature. Full-precision, fused-PQ and PQ-sidecar sources are all
still supported, through the same entry points as before.

**How to Enable**

No configuration required, and no system properties are introduced. The behaviour is fixed at the
measured operating point: merged cells, probe beam width 64, scan budget 4,096 vectors per larger
partition.

The cell join engages when the merged upper layers yield level-1 nodes and the similarity function
is dot product, Euclidean or cosine. If either does not hold — for example merging flat indexes with
no hierarchy — level 0 falls back to the existing per-node graph search and output ordinals fall
back to a PQ-code prefix. The merge is correct either way; only the level-0 strategy changes, and
the compactor logs which path it took.

**Results**

Three datasets of 6M to 10M vectors, four partitions each, graph degree 32, 64 threads, cold page
cache before every run, no swap, one run at a time on a 32-physical-core host with 495 GB RAM and
NVMe RAID 0. Memory is a cgroup v2 `MemoryMax` set as a fraction of the on-disk input index size S.
**Ratio is S divided by that limit**, so ratio above 1 means the index does not fit in the memory the
process may use.

Speedup is the previous implementation's compaction time divided by the new one's.

| Dataset | dim | unconstrained | ratio 1.00 | ratio 1.33 | ratio 1.97 |
|---|---|---|---|---|---|
| CAP-6M | 1536 | 2.10× | 2.54× | est. 16× | est. 47× |
| DPR-10M | 768 | 2.58× | 3.05× | est. 28× | est. 76× |
| Cohere-10M | 1024 | 2.63× | 2.50× | **9.72×** | est. 40× |

Values marked `est.` are runs where the old implementation was stopped once it had taken ten times
the new one's wall clock; their throughput is measured over the nodes actually completed, so those
figures are lower bounds on the gap. 9.72× is the one above-RAM figure where both implementations
ran to completion.

The mechanism is visible in the fault counts. The old implementation services major faults at a
near-constant rate, so its wall clock is essentially its fault count divided by a constant, and
memory pressure multiplies that count:

| Dataset | major faults/node, ratio 1.00 | ratio 1.33 |
|---|---|---|
| CAP-6M | 43.1 | 472 |
| DPR-10M | 40.9 | 582 |

The cell join moves from 4.07 to 4.26 and from 2.64 to 2.86 over the same step. On CAP-6M at ratio
1.97 both implementations spend almost identical *user* CPU, 44,764 s against 46,816 s, so they
compute comparable distances; the old one then adds 349,979 s of kernel time servicing page faults
and spends 80% of its wall clock stalled on I/O at 17% CPU utilisation, against 76% for the cell
join.

Throughput, nodes per second, shows the same thing from the other side: the cell join varies by only
1.24× to 1.39× across the entire memory range and tracks vector width rather than available memory,
while the old implementation falls by 20× to 41×.

**Quantized inputs**

At ratio 1.33, by input layout:

| Layout | Speedup | Recall change |
|---|---|---|
| fused PQ | 2.34× – 4.58× | −0.23 to +1.54 pt |
| full precision | est. 16× – 28× | see below |
| PQ sidecar | est. 20× – 47× | not measured |

The ordering is explained entirely by whether the old implementation can navigate on codes. Fused
codes are inline and it uses them, so its faults fall to 43–75 per node and the gap narrows.
Full-precision sources have no codes. A PQ sidecar is the worst case for it: codes exist but are
only consulted when written inline, so a sidecar's codes are retrained and rewritten yet never
navigated on, and its faults rise to 474–962 per node.

**Notes and trade-offs**

*Recall.* On full-precision inputs the cell join gives up **0.3 to 1.0 points of recall@10**. The old
implementation's recall is identical to five decimal places at every memory setting, so it is
deterministic; the cell join varies about 0.4 points run to run, from thread scheduling and a
per-run wide-code retrain, which puts the smallest deficits inside its own noise. On fused inputs
the deficit disappears.

*Attribution.* The figures above compare against `main`, which is what users have today, so they
credit this change with everything in the PR rather than the cell join alone. Measured against the
same branch with the cell join switched off and its other changes kept, the cell join is **1.4× to
1.6× slower in RAM**: most of the in-RAM gain comes from processing partitions smallest-first with
bounded reverse offers, which halves the number of searches. The cell join's own contribution is the
above-RAM columns, where it converts scattered reads into sequential ones.

*Scope.* Every behavioural change is confined to the compaction path. Outside it, four files are
touched and all four are additions only: a `dotProductMulti` kernel added to `VectorUtilSupport` as
a **default method**, so existing implementors are unaffected, its Panama override, a static entry
point on `VectorUtil`, and three read-only getters on `ProductQuantization`. Eighty-four lines added,
none removed, and no existing non-compaction code path is modified or re-routed.

*Measurement scope.* All figures are a single run per configuration; repeats were not taken. Where
the old implementation was stopped the effect sizes are above 10×, far outside the run-to-run
variation observed elsewhere, but the completed in-RAM and ratio-1.00 comparisons should not be read
to two decimal places.
