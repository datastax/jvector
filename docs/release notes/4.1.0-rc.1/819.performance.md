### Faster Exact-Score Search

**Description**

The exact score functions score a node's unvisited neighbors with one bulk call instead of one call per neighbor,
and the Panama provider scores four of them per pass, which keeps four vectors' memory loads in flight. Each
target accumulates exactly as the pairwise kernel does, so scores, search results and built graphs are unchanged.
See [#818](https://github.com/jbellis/jvector/issues/818).

New API: `VectorSimilarityFunction.compare(q, targets, count, results)`, the matching bulk methods on `VectorUtil`
and `VectorUtilSupport`, and `ScoreFunction.supportsBatchScoring()`, which the search path asks before it gathers a
node's neighbors.

**How to Enable**

No configuration is required for `DefaultSearchScoreProvider.exact` and `BuildScoreProvider.randomAccessScoreProvider`.
A custom `ExactScoreFunction` benefits once it implements the bulk `similarityTo` and reports
`supportsBatchScoring()`, for example by fetching the vectors and calling
`VectorSimilarityFunction.compare(q, targets, count, results)`.

**Notes**

On an AVX-512 Xeon with 100,000 1024-dimension COSINE vectors, single-threaded exact search over a graph in memory
went from about 1,270 to about 1,820 queries per second on the same graph.

The gain comes from scoring the targets of a node together, so it needs a source that hands out its vectors
without copying them. A source that materializes a vector per call spends its time in the copy instead, and the
bulk path is then slower than the pairwise one (about 750 instead of 810 queries per second in that case, and a
build that takes about 6% longer).
